# API変更の整合性チェック

複数ファイルにまたがるAPI変更の整合性を確認してください。

## チェック観点

### 1. インターフェース変更の一貫性
- APIの定義変更（関数シグネチャ、クラスインターフェース等）に対して、すべての呼び出し側が更新されているか
- 引数の追加・削除・型変更が正しく反映されているか
- 戻り値の型変更が適切に処理されているか

### 2. 後方互換性の確保
- 既存のAPIに破壊的変更が含まれていないか確認
- 破壊的変更がある場合：
  - バージョニング戦略（APIバージョンのインクリメント等）
  - 非推奨（deprecated）マークと移行期間の設定
  - 移行ガイドやドキュメントの更新

### 3. エンドポイント変更の完全性
- RESTful APIやGraphQLのエンドポイント変更において：
  - ルーティング定義が正しく更新されているか
  - フロントエンド側のAPI呼び出しが対応しているか
  - APIドキュメント（OpenAPI/Swagger等）が更新されているか
  - 認証・認可の処理が適切に実装されているか

### 4. データ契約の整合性
- リクエスト/レスポンスのスキーマ定義が一致しているか
- バリデーションルールが統一されているか
- エラーレスポンスの形式が一貫しているか

### 5. 依存関係の影響分析
- 変更が他のモジュール・サービスに与える影響を評価
- マイクロサービス間の通信プロトコル変更の影響
- 外部APIの統合に影響がないか

### 6. テストカバレッジ
- 変更されたAPI仕様に対応するテストが追加・更新されているか
- 統合テスト、E2Eテストが必要な場合は含まれているか
- モックやスタブが適切に更新されているか

## 出力形式

以下の形式で整合性チェックの結果を報告してください：

### API変更サマリー
- 変更されたAPI一覧とその影響範囲

### 整合性チェック結果
**[OK/NG] チェック項目**
- 詳細説明
- 問題がある場合は具体的な指摘と推奨対応

### 総合評価
- 変更が安全にデプロイ可能かの判定
- リスクがある場合の推奨される対応順序

問題がない場合は「API変更の整合性に問題なし」と記載してください。
